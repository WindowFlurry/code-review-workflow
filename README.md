# 代码审查助手

> 这个仓库里装了**两个作业**：
>
> | 作业 | 内容 | 从哪看 |
> |---|---|---|
> | **作业一** | 代码审查 Agent | 就是下面这份 README |
> | **作业二** | 编码 → 审查 → 修复 多 Agent 工作流 | [`docs/WORKFLOW.md`](docs/WORKFLOW.md) |
>
> 作业二**复用了作业一的审查 Agent** —— 工作流里最重的那一步直接调用作业一的图。
> 双击 `3-运行Workflow.bat` 就能看作业二跑起来。

一个基于 **LangChain + LangGraph**、使用 **DeepSeek** 的代码审查助手。

你给它一个文件夹或一个 `.py` 文件，它会读完代码，列出发现的问题，
并说明**哪个文件、第几行、什么毛病、怎么改**。

它最大的特点是：**每一条结论都会拿真实文件核对一遍**。AI 说"第 17 行有问题"，
程序就真的去打开文件对一次；对不上，这条结论直接丢掉，不会给你看。

```
┌──────────────────────── 摘要 ────────────────────────┐
│ 共检查 3 个文件，在 3 个文件中发现 11 个问题         │
│ （高 2 条、中 5 条、低 4 条）。                       │
└──────────────────────────────────────────────────────┘

1. [高] input 返回字符串，加法把两个数字拼接而不是相加
   计算器.py:16-19   缺陷
   `input()` 返回的是 str，所以 "1" + "2" 得到 "12" 而不是 3。
       def 计算(第一个数, 第二个数, 运算符):
   修改建议： 第一个数 = float(input("请输入第一个数："))
```

## 一、怎么用（最简单的方式）

桌面上有个文件夹叫 **`agent making`**，里面有两个可以双击的文件：

| 双击这个 | 作用 |
|---|---|
| **`1-运行示例.bat`** | 检查自带的示例代码，看效果。大约 10~30 秒 |
| **`2-审查我的代码.bat`** | 检查你自己的代码。把文件夹或 `.py` 文件**拖进黑窗口**，按回车 |
| **`3-运行Workflow.bat`** | **作业二**：跑一次「编码 → 审查 → 修复」多 Agent 工作流 |

> 拖进去之后路径外面会自动带一对引号，那是正常的，程序会自己处理。

### 作业二的两个玩法

`3-运行Workflow.bat` 按你输入的东西自动选路：

| 你输入 | 会发生什么 | 花钱吗 |
|---|---|---|
| **直接按回车** | 回放一次跑好的示例，看流程长什么样 | **不花钱** |
| 一段文字，比如「写个判断回文的函数」 | 三个 Agent 全上：编码 Agent 写代码 → 审查 → 修复 | 几分钱 |
| **把一个 `.py` 文件拖进去** | **跳过编码 Agent**，直接审你自己写的代码 → 有问题就让修复 Agent 改 | 几分钱 |

示例用的是 `示例代码\工作流演示\两数相加.py`（一个加减法写错、变量名拼错的
小文件）。回放的结果是事先真跑一次存下来的，终端会明确标出「这是回放」。

跑完之后，黑窗口里会按顺序列出**每一步是谁、读了什么、写了什么、改了几行**，
以及每一轮代码的 diff（绿色是新增，红色是删除）。想看完整的就打开
`runs\工作流\<时间戳>\workflow-report.md`。

- 黑色的窗口是正常的，不是出错。
- 跑完按任意键关掉窗口。
- 完整报告存在 `runs` 文件夹里，用记事本打开 `report.md` 就能看。
- 每跑一次大约花**几分钱**（用你的 DeepSeek 账号）。

## 二、为什么要做"核对"这件事

AI 有个很麻烦的毛病：**它会一本正经地胡说八道**。

比如它告诉你"你第 50 行有个 SQL 注入漏洞"，你打开文件一看——文件总共只有 30 行。
一旦出现这种情况，整份报告你都不敢信了，包括那些本来是对的条目。

所以这个助手把"不许瞎编"当成头号问题来解决，用了三道关卡：

| 关卡 | 做什么 |
|---|---|
| **① 先跑静态检查** | 用 ruff 和 Python 自带的语法分析找问题。这些结果是机器算出来的，**不可能编造** |
| **② 证据核对** | AI 报"第 17 行有 `eval(...)`"，程序就**重新打开文件读第 17 行**，逐字符比对。对不上，这条直接丢弃；对得上，报告里显示的代码**用文件里的原文**，不用 AI 打的字 |
| **③ 换个 AI 复核** | 让另一个 AI 专门挑刺："刚才说这里有 bug，证据呢？" 它的默认答案是"不成立"，除非代码本身就能证明 |

第 ② 关是关键：**AI 对最终报告里显示什么代码，没有任何控制权**。所以哪怕代码里写了骗 AI 的话，也进不了报告。

而且被丢弃的条数会**明明白白打印出来**。给一份完全没问题的代码，你会看到：

```
AI 提出的候选  7
        已否决  7 条（证据对不上 7 条）
```

这才是"它真的在核对"的证据，而不是嘴上说说。

## 三、它内部是怎么工作的

```
开始
 │
 ├─ [清点]      机器做：列出所有文件，跳过二进制文件、超大文件
 │               （文件夹是空的 → 直接跳到出报告）
 │
 ├─ [静态扫描]   机器做：全项目跑一遍 ruff + 语法分析
 │
 ├─ [制定计划]   AI 做：决定先看哪些文件
 │
 ├─ [逐文件审查] AI 做：每个文件派一个 AI 去读，可以用工具查代码
 │               → 读完后立刻做"证据核对"
 │
 ├─ [复核]       AI 做：另一个 AI 逐条挑刺
 │
 ├─ [汇总去重]   机器做：合并重复的、按严重程度排序
 │
 └─ [出报告]     机器做：终端显示 + Markdown 文件 + JSON 文件
```

**设计原则是："能算的就别猜。"**

文件有多少、第几行、用了哪个变量——这些都能精确算出来，就交给程序算。
只有"这段代码到底有没有问题"需要判断，才交给 AI。而 AI 每次判断，
都要能被某个"不是 AI 生成的东西"验证。

用到的设计模式：**ReAct**（推理→用工具→观察）、**反思/生成-验证**（第二个人复核）、
**Map-Reduce 扇出**（多个文件同时审）、**计划-执行**（先规划再动手）。

详细说明见 [`docs/DESIGN.md`](docs/DESIGN.md)。

## 四、安装（换电脑时用）

需要 **Python 3.10 以上**（开发环境是 3.13.9，Windows 11）。

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows
pip install -r requirements.txt
```

配置密钥：

```bash
cp .env.example .env
```

然后编辑 `.env`，填一行：

```
DEEPSEEK_API_KEY=sk-你的密钥
```

> 注意模型名要用 `deepseek-flash`。网上很多教程还在写 `deepseek-chat`，
> 那个名字**已经停用**了，照抄会报错。

先自检一下再开始用：

```bash
python -m codereview doctor
```

```
代码审查助手 版本 0.1.0
正常  AI 密钥已配置（尾号 7f2b）
     使用的模型：deepseek-flash
正常  ruff 静态检查工具可用
正常  langchain 1.4.3、langgraph 1.2.12
正常  真实调用成功（返回 'ok'）

一切正常，可以开始使用了
```

`doctor` 会真的调一次 AI，所以密钥错了、模型名写错了，都会在这一步就发现，
而不是等你跑了半天才失败。

## 五、命令行用法

```bash
# 审查一个文件夹
python -m codereview review ./我的项目

# 审查单个文件
python -m codereview review ./我的项目/main.py

# 只看静态检查，不调用 AI（不花钱、几秒钟）
python -m codereview review ./我的项目 --offline

# 输出干净一些，只显示报告
python -m codereview review ./我的项目 --quiet
```

审完之后可以追问，**关掉程序再开也能接着问**（对话存在文件里）：

```bash
python -m codereview ask --repl
> 第 3 条为什么算安全问题？
> 给我看看怎么改
> 你检查过 utils.py 吗？
```

网页界面（可选）：

```bash
python -m streamlit run src/codereview/web.py
```

### 单独使用某个工具（不调用 AI）

```bash
python -m codereview tools list  ./我的项目          # 列出文件
python -m codereview tools read  ./我的项目 app.py   # 带行号读文件
python -m codereview tools lint  ./我的项目          # 跑 ruff
python -m codereview tools ast   ./我的项目 app.py   # 看函数结构
python -m codereview tools search ./我的项目 "def "  # 搜索代码
```

## 六、它能处理哪些"意外情况"

每一条都有对应的测试，运行统计里也会报告遇到了几次：

| 情况 | 处理方式 |
|---|---|
| 二进制文件伪装成 `.py` | 检测到空字节，跳过并说明原因 |
| UTF-16 / GBK 编码的文件 | **正常审查**（简单做法会把它当二进制文件丢掉） |
| 有语法错误的文件 | 由语法分析工具报告，**不交给 AI 猜** |
| 超过 256KB 的文件 | 标记为"过大"跳过，并计数 |
| 空文件夹 | 直接给出说明，不调用 AI，零花费 |
| **代码完全没问题** | 报告"未发现问题"——**绝不编造问题凑数** |
| AI 服务临时抽风 | 自动重试；还可以配置备用模型 |
| 密钥错 / 余额不足 | 立刻报错，不做无意义的重试 |
| AI 返回格式不对 | 计数并丢弃，不会当成问题报出来 |
| 工具执行出错 | 转成提示信息交给 AI，让它自己调整 |
| 某个文件审失败了 | 记录下来，**其他文件照常审完** |

报告底部的统计栏会把跳过了几个、丢弃了几条都列出来。

## 九、文件夹结构

```
agent making/
├─ 1-运行示例.bat          ← 双击：看效果
├─ 2-审查我的代码.bat      ← 双击：审自己的代码
├─ 3-运行Workflow.bat      ← 双击：作业二的多 Agent 工作流
├─ 示例代码/                ← 带典型错误的示例，可以拖进窗口试
├─ README.md               ← 你正在看的这份
├─ docs/
│   ├─ DESIGN.md           ← 设计文档：为什么这么做
│   ├─ EVALUATION.md       ← 实测数据：准确率多少
│   └─ WORKFLOW.md         ← 作业二：流程、协作、扩展性
├─ src/codereview/         ← 程序代码
│   ├─ agent/              流程编排、各个 AI 角色
│   ├─ workflow/           作业二：编码 → 审查 → 修复
│   ├─ verification/       证据核对、去重 ← 最关键的部分
│   ├─ tools/              读文件、搜索、跑 ruff、分析语法
│   ├─ ingestion/          遍历文件夹、识别编码
│   ├─ llm/                AI 模型配置
│   ├─ report/             出报告的三种格式
│   ├─ memory/             对话记忆
│   └─ cli.py              命令行入口
├─ tests/                  测试
├─ scripts/                辅助脚本（备份还原点）
└─ runs/                   每次运行的产物
```
