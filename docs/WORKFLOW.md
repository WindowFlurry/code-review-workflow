# 作业二：编码 → 审查 → 修复 多 Agent 工作流

## 一、做了什么

三个 AI Agent 分工协作，把一个自然语言需求变成一份经过审查和修复的代码：

> 你说「写一个函数，把嵌套字典展平」→ 编码 Agent 写出代码 → 审查 Agent 挑毛病
> → 修复 Agent 按报告改 → 再送回审查 → 直到没问题为止。

对应 PPT 里的方向**「代码审查流程（编码 → 审查 → 修复）」**。

### 三处流程控制

| PPT 要求 | 本项目怎么做的 |
|---|---|
| **顺序执行**（必须） | 编码 → 审查，固定顺序 |
| **条件分支**（推荐） | ① 编码失败就跳过审查直接收尾；② 「还有需要修的问题吗」决定进入修复还是收尾 |
| **循环**（推荐） | 修复完回到审查重来，最多 `max_rounds` 轮（默认 3） |
| 并行执行（推荐） | **未采用**——这条流程天然是串行的，强行并行只会让状态变复杂。但审查那一步内部有并行：作业一的图会同时审查多个文件 |

## 三、三个 Agent

| Agent | 职责 | 输入 | 输出 | 实现 |
|---|---|---|---|---|
| **编码** | 需求变代码 | 自然语言需求 | 完整 Python 文件 | 新写，`workflow/agents.py` |
| **审查** | 找问题 | 工作目录 | **已验证的**问题清单 | **复用作业一** |
| **修复** | 按报告改代码 | 代码 + 问题清单 | 修复后的完整文件 | 新写，`workflow/agents.py` |

### 为什么这样分工

每个 Agent 只干一件事，而且**干的这件事它有能力干好**：

- 编码 Agent 不需要知道怎么审查，它只需要会写代码
- 审查 Agent 不需要知道代码是谁写的，它只需要会挑毛病
- 修复 Agent 不需要自己找问题，它只需要照着报告改

分工带来的一个实际好处：**可以单独替换任何一个 Agent**，其他两个不用动。
比如把编码 Agent 换成调另一个模型，审查和修复完全不受影响。

## 四、Agent 之间怎么通信

**三个 Agent 不直接对话，而是读写同一份共享状态。**

```python
class WorkflowState(TypedDict):
    requirement: str              # 需求      ← 调用方写，编码 Agent 读
    code: str                     # 当前代码   ← 编码/修复写，审查/修复读
    findings: list[VerifiedFinding]  # 问题清单 ← 审查写，修复读
    round: int                    # 第几轮     ← 修复写，判断节点读
    steps / rounds / usage / errors  # 执行日志，所有节点都写
```

数据是**单向流动**的，方向清楚：

```
需求 ──→ [编码] ──→ code ──→ [审查] ──→ findings ──→ [修复] ──┐
                      ↑                                        │
                      └────────────────────────────────────────┘
                                    改完的代码写回 code
```

### 状态管理上的两个细节

**1. 并行字段用归纳器合并，不互相覆盖**

```python
steps:  Annotated[list[WorkflowStep], operator.add]
usage:  Annotated[list[Usage], operator.add]
errors: Annotated[list[str], operator.add]
```

`operator.add` 表示「多个节点都往这个列表里加东西时，合并而不是覆盖」。
作业一里并行审查多个文件也是同样的做法。

**2. 快照写在产物目录，不写在工作目录**

工作目录是审查 Agent 的扫描范围。如果把每一轮的历史代码也放进去，
下一轮审查就会把上一轮的旧文件当成待审代码，报告里会冒出一堆莫名其妙的问题。
所以快照统一写到旁边的产物目录里。

## 六、两个值得说的设计决定

### 1. 编码/修复 Agent 没有「写文件」的工具

作业一的工具**全是只读**的，当初是刻意的：AI 碰不到文件系统，就不可能改坏东西。

编码和修复要产出代码，有两条路：

- 给它们新建一套「写文件」工具 —— 要额外处理沙箱写入、路径逃逸、并发写冲突
- **让它们返回完整的代码文本，由工作流负责写盘** ← 选了这条

结果一样（文件写出来了），但 **AI 始终碰不到文件系统**，它只能在结构化的
返回值里填一段字符串。安全边界一点没松动。

### 2. 退出条件按「类别 + 等级」判断，不只看等级

一开始的规则是「只有高危问题才继续修」。实测发现这不够：

> 审查 Agent 报出一个真正的 bug：`flatten_dict({})` 返回 `{'': {}}` 而不是 `{}`。
> 合法输入下结果就是错的。但它被标成「中」等严重度，于是被跳过、没有被修。

**一个会在合法输入上给出错误结果的 bug，不该因为它没让程序崩溃就被放过。**

所以规则改成两条并集：

```python
def is_actionable(finding) -> bool:
    return finding.severity in ("critical", "high")   # 等级高
        or finding.category in ("bug", "security")    # 或者属于缺陷/安全
```

风格和可维护性方面的意见仍然不触发修复 —— 那种问题修不完。

## 七、怎么用

工作流有两种用法，入口会自动分流：

```
START ── 状态里有代码吗？
           ├── 有（你给的）──→ 审查 ──→ ...
           └── 没有 ─────────→ 编码 ──→ 审查 ──→ ...
```

### 用法一：让 AI 写代码

给一句需求，三个 Agent 全部参与：编码 Agent 写，审查 Agent 挑毛病，
修复 Agent 改。

```bash
python -m codereview workflow "写一个函数，判断字符串是不是回文"
```

### 用法二：审你自己写的代码

用 `--code` 指定文件。**跳过编码 Agent**，直接从审查开始，
参与协作的是审查和修复两个 Agent：

```bash
python -m codereview workflow --code 示例代码\成绩统计.py
```

这条路径的意义在于：代码是你写的，所以「AI 改了哪里」是**有意义的对比**——
原来的 bug 就在你眼前，改完之后 diff 一摆，改了什么一目了然。

### 双击运行

双击项目里的 **`4-运行Workflow.bat`**：

- 直接按回车 → 用内置需求，走「让 AI 写」那条路
- 输入一段文字 → 当成需求，走「让 AI 写」
- **把 `.py` 文件拖进窗口** → 自动走 `--code`，审你的代码

### 其他选项

```bash
--max-rounds 2      # 最多修 2 轮（默认 3）
--out 某个目录       # 换个产物目录
--verbose           # 打开详细日志
```

### 产出

每次运行都会新建一个**带时间戳**的独立目录（默认 `runs/工作流/<时间戳>/`），
多次运行互不干扰：

| 文件 | 内容 |
|---|---|
| `workflow-report.md` | 完整报告：过程、代码改动、结果、最终代码、统计 |
| `workflow-report.json` | 同样的内容，给程序读的 |
| `round-0-初始生成.py` | 编码 Agent 最初写出来的代码 |
| `round-0-你提供的代码.py` | `--code` 模式下，你交进来的原始代码 |
| `round-1-修复后.py` | 第 1 轮修完之后的样子（有几轮就有几份） |
| `workspace/solution.py` | 最终代码 |
| `agent.log` | 逐步骤的执行日志 |

**每一轮的代码都留了快照**，可以对比着看「这一轮到底改了什么」。

## 七之二、协作过程怎么看见

这是作业二最容易被含糊过去的地方：「多 Agent 协作」如果只是代码里传了几个
变量，验收时是看不出来的。所以终端输出里做了三处，都直接对应评分点：

### 1. 「读 → 写」列 —— 谁把什么交给了谁

```
┌──────┬────────────┬──────────────────┬──────────────────────────┐
│ 轮次 │ 谁         │ 读 → 写          │ 做了什么                 │
├──────┼────────────┼──────────────────┼──────────────────────────┤
│ 初始 │ 编码 Agent │ 需求 → 代码      │ 生成代码 42 行           │
│ 初始 │ 审查 Agent │ 代码 → 问题清单  │ 第 1 轮审查完成，发现 1 条│
│ 第1轮│ 修复 Agent │ 代码+清单 → 代码 │ 第 1 轮修复完成，改动 6 行│
│ 第1轮│ 审查 Agent │ 代码 → 问题清单  │ 第 2 轮审查完成，发现 0 条│
└──────┴────────────┴──────────────────┴──────────────────────────┘
```

三个 Agent 不互相调用、不互相对话，全靠共享状态传数据。这一列把每一次
「谁读了什么 / 写了什么」列出来，**协作的链路就是看得见的**：
编码写 `code` → 审查读 `code` 写 `findings` → 修复读 `code` + `findings`
写 `code` → 审查再读 `code`。

### 2. 代码改动 —— AI 到底改了什么

每一轮修复都会算一次 diff（`difflib.unified_diff`），终端里绿加红删：

```diff
@@ -12,7 +12,9 @@
 def load(text):
     try:
         return json.loads(text)
-    except:
+    except json.JSONDecodeError as exc:
+        logger.warning("解析失败：%s", exc)
         return None
```

报告里还有一行字说明这轮改了几行。

### 3. 停止原因 —— 流程控制的结果

最后一块面板明说**为什么停**：是「审干净了」还是「到轮数上限了」。
这是 `decide()` 条件分支的直接输出。

## 八、可扩展性

PPT 的评审标准里「可扩展性」占 20%。这个架构在这几个方向上都留了口子：

### 新增一个 Agent

比如想加一个「测试生成 Agent」，在审查之后跑：

```python
# 1. 写提示词和结构化输出（workflow/agents.py）
# 2. 写节点函数（workflow/nodes.py）
def test_gen_node(state) -> dict:
    ...

# 3. 在图里插一个节点（workflow/graph.py）
graph.add_node("test_gen", test_gen_node)
graph.add_edge("review", "test_gen")      # 改一条边
graph.add_edge("test_gen", "report")
```

**三个地方，每个都是加几行。** 原有节点不用动。

### 换掉某个 Agent

三个 Agent 之间只通过状态通信，不互相依赖实现。
把编码 Agent 换成调用另一个模型，只要新 Agent 还是「需求进、代码出」，其他都不用改。

### 改流程控制

退出条件集中在 `decide()` 一个函数里（`workflow/nodes.py`）。
想改成「修到完全没有问题为止」、「最多花 1 块钱」、或者「按类别分别限制轮数」，
都只需要改这一个函数。

### 改产出规模

目前限定单文件（`SOLUTION_FILENAME` 是个常量）。
要支持多文件的话，把状态里的 `code: str` 换成 `files: dict[str, str]` 即可，
审查那一步不用改（作业一的图本来就是按目录审查多个文件的）。

## 九、测试

```bash
pytest tests/test_workflow.py     # 30 项，不联网、不花钱
```

三个 Agent 全部用假的替换，所以整条流程——编码、审查、判断、修复、汇总，
包括循环和条件分支——都能离线跑完。**只有模型的「判断」是假的，
流程控制、状态传递、快照落盘、报告生成都是真代码。**

覆盖的场景：

| 场景 | 验证什么 |
|---|---|
| 一次就审干净 | 不该进入修复 |
| 报高危 | 修一轮之后再审，然后结束 |
| 一直修不好 | 卡在轮数上限，不会无限循环 |
| 只有风格意见 | 不触发修复，但仍然报表出来 |
| **中等的真 bug** | **触发修复**（回归测试，见上面第六节） |
| 编码失败 | 跳过审查直接收尾 |
| 审查本身出错 | 不在循环里打转 |
| 模型加了 ``` 代码围栏 | 落盘前擦干净 |
| 快照位置 | 写进产物目录，不能污染工作目录 |

## 十、实测记录

**需求**：把嵌套字典展平成单层字典，键用点号连接

```
初始   编码   生成代码 42 行
初始   审查   发现 1 条问题（S112，需要修复）
第1轮  修复   48 行，在 except 分支里加了日志记录
第1轮  审查   发现 0 条问题
       → 干净通过
```

三次运行的典型耗时 10~60 秒，花费约 0.3~0.5 元。

注意模型每次写出来的代码不完全一样，所以有时第一轮就干净通过、不进循环。
**循环会不会触发取决于编码质量，不确定** —— 这是这类系统的正常现象，
所以退出条件里必须有不依赖模型表现的硬上限兜底。
